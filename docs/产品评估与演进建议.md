## 一、P0 致命缺陷：本地写服务一击必崩

### 现象（已实测复现）

```
$ node tools/serve.js
简历编辑器已启动 → http://localhost:8000
...
ReferenceError: u is not defined
    at Server.<anonymous> (tools/serve.js:287:33)
Node.js v22.22.2          ← 进程直接退出
```

```
$ curl -o /dev/null -w '%{http_code}' '127.0.0.1:8000/api/library/doc?id=default'
000                        ← 连接被拒，服务已死
```

### 根因

`tools/serve.js:222-230` 把 URL 对象定义在 `try` 块**内部**：

```js
let pathname;
try {
  const u = new URL(req.url, 'http://localhost');   // ← 块作用域，出了 try 就没了
  pathname = decodeURIComponent(u.pathname);
} catch (e) { return send(res, 400, ...); }
```

而三处接口在块外引用它（同一根因，**不止一处**）：

| 行号 | 接口 | 触发方式 |
|---|---|---|
| `serve.js:287` | `/api/library/doc`（GET/POST/DELETE） | **前端启动必经路径** |
| `serve.js:546` | `/api/feishu/register/poll` | 扫码注册个人应用时轮询 |
| `serve.js:598` | `/api/feishu/register/cancel` | 关闭二维码 |

讽刺的是，第 222 行的注释写着「URL 解析容错：绝不让异常穿透到进程」——**注释承诺的事，代码在 65 行后就违反了**。

### 为什么它一次就崩，而且崩得彻底

1. 异常发生在 `http.createServer` 的**同步回调**里 → 无人 catch → 触发 `uncaughtException` 默认行为 → **进程退出**。
2. 全文件（718 行）**没有任何** `process.on('uncaughtException')` / `unhandledRejection` 兜底（已 grep 确认为空）。
3. 同类裸调用还有 `serve.js:433`（`feishuSync.readConfig()`）、`:504`（`feishuOauth.status()`）、`:509`（`clearOauth()`）——同样是「抛错即杀进程」。

### 影响链（这才是可怕的地方）

```
打开「简历库」页(#/library) 或任何触发 loadDoc 的动作
        ↓
服务进程退出（本地写服务彻底失效）
        ↓
前端 fetch 失败 → resume-library.js 永久降级到 localStorage（无自动恢复）
        ↓
写盘静默失败被 try{}catch{} 吞掉（app.js:470）→ 界面无任何提示
        ↓
用户以为「已经保存了」，实际上磁盘上什么都没有
```

**这是数据丢失类事故，且用户完全看不见。** 这也是为什么它至今没被发现——因为用户在用的还是旧的单份 `data/resume.json` 路径（见 §二），恰好绕开了这条路。

### 修复（约 5 行）

```js
let pathname, u;                       // 提到 try 之外
try { u = new URL(req.url, 'http://localhost'); pathname = decodeURIComponent(u.pathname); }
catch (e) { return send(res, 400, { error: 'Bad Request: malformed URL' }); }
```

再加一道进程级兜底（否则下一个同类 bug 还是会杀进程）：

```js
process.on('uncaughtException', (e) => console.error('[未捕获异常]', e));
process.on('unhandledRejection', (e) => console.error('[未处理拒绝]', e));
```

> ⚠️ 兜底只做「不杀进程」，真正的修复仍是消灭 `u` 越界与把 `:433/:504/:509` 收进 try。

## 二、数据模型落地缺口：多简历库形同虚设

README 宣称「已统一为分文件模型：一份简历 = 一个文档（`resumes/<id>.json`）」，但**实际磁盘状态**是：

```
data/
└── resume.json        ← 30KB，2026-09-20 18:44（今天下午还在用）
    （没有 data/resumes/ 这个目录）
```

实测界面也印证了不一致：

- 打开编辑器：一份内容完整的简历正常显示 ✅
- 打开「简历库」`#/library`：**「还没有简历 · 从一份空白简历开始，或导入已有的 PDF / JSON」** ❌

也就是说：**同一个应用里，编辑器说「你有一份简历」，简历库说「你一份都没有」。**

可能的成因（需进一步确认）：README 承诺的「首次启动自动把 `resume.json` 迁移进简历库」这一步没有真正完成——而迁移正需要调用 `saveDoc` → 命中 §一 的崩溃点，形成死锁：**想迁移 → 触发崩溃 → 迁移永远失败**。

### 为什么这件事比看起来严重

1. 用户会看到自相矛盾的状态，且**不知道该信哪个**；
2. 所有依赖简历库的能力（多简历、复制、重命名、导入 PDF 为多份、飞书按 id 分键同步）**全部建立在一条从未跑通的路线上**；
3. 文档与实际不符，会让下一个接手的人（包括未来的你）基于错误前提做决策。

### 建议

- 先修 §一，再写一个**显式的一次性迁移**（带进度提示与失败可重试），并在设置页加「数据体检」入口显示：当前数据源、检出条目数、磁盘路径、最后写入时间。
- 把「迁移成功」变成一件**用户能看见的事**，而不是后台静默尝试。

## 三、测试可信度：371 条全绿，为何抓不到 P0

实测：`node test/run.js` → **pass=371 fail=0**，与 README 一致。但上面那个一击必崩的 bug 全数逃过。

原因有三个层次：

**1. serve.js 从未被真正执行过**

`test/run.js:439-476` 只是把 `tools/serve.js` **读成字符串**，用正则匹配 `/api\/feishu\/register\/begin/` 之类的片段，确认「接口存在」。它不发起任何 HTTP 请求。所以 `u is not defined` 在 CI 里**结构上不可能被发现**。

**2. DOM 桩没有「同一性」，交互链路测不了**

`test/run.js:63`：`getElementById() { return makeEl(); }` —— 每次返回**全新对象**；`querySelectorAll()` 恒返回 `[]`。这意味着这条链路：

```
innerHTML 写入 → 查询子节点 → 派发事件 → 冒泡到委托监听器
```

**根本无法成立**。`test/cases.js`（174 行）里 `dispatchEvent` / `.click(` 出现 **0 次** —— 测试只覆盖纯逻辑，从不覆盖真实交互。

**3. 大量断言是「源码正则」而不是「行为执行」**

`test/run.js:325-496` 大量使用正则匹配 CSS/HTML/JS 文本。这类断言只能防「文件被误删」，防不了「逻辑写错」。

### 建议（零依赖，成本可控）

- **HTTP 冒烟测试**：用 Node 内置 `http` 模块，在随机端口**真起 serve.js 子进程**，至少覆盖 `/api/library/doc` 的 GET/POST/DELETE、`/api/library/index`、敏感文件（`sync.config.json`）必须 403、非法 id 必须 400。这一条能立刻抓住本次 P0。
- **给 DOM 桩加同一性**：用一个 `Map` 缓存 `getElementById` 的结果（同名返回同对象），让「写入 → 查询 → 派发」链路可测；这需要写一个约 150 行的迷你 DOM 桩，但能解锁大量交互回归测试。
- **把「正则断言」逐步换成「行为断言」**，优先替换与安全/数据相关的那些。

## 四、架构与技术债

### 4.1 `app.js` 仍是事实上的上帝对象

- 暴露 **72 个** `ResumeEditor.*` 成员
- `index.html` 有 **51 处**内联 `on*`，其中 33 处直接调 `ResumeEditor`
- 另有 **16 个 `RB.*` 桥接**（`app.js:679-696`）供拆出去的模块反向回调

`resume-render.js` / `export-pdf.js` 通过 `window.RB` 反向依赖 `app.js` 内部状态，形成**双向隐式耦合**——加载顺序错了就静默失效，而没有任何机制能检查它。

### 4.2 全局命名空间互相覆盖（定时炸弹，当前侥幸不炸）

```js
// js/export/export-pdf.js:242
global.ResumeExport = { exportPDF, downloadPDFNow, closePdfModal, showExportModal,
                        closeExportModal, doExportDownload, exportLongImage, exportSingleFileHTML };

// js/export-extra.js:466        ← 后加载，整包覆盖上面那个
global.ResumeExport = { exportDocx, exportTxt, exportMarkdown, exportPdfSilent,
                        buildDocx, buildPlain, buildBlocks, zipStore, crc32 };
```

两者键**零重叠**，而后加载者整包覆盖前者。`index.html` 的加载顺序是 export-pdf.js（:287）在前、export-extra.js（:300）在后，所以最终 `window.ResumeExport` **丢掉了 8 个函数**（`exportPDF` / `exportLongImage` / `exportSingleFileHTML` / `downloadPDFNow` / `closePdfModal` / `showExportModal` / `closeExportModal` / `doExportDownload`）。

**今天不炸，只因为** `app.js:14` 在 export-extra.js 加载**之前**就解构了这 8 个引用到局部变量。任何一次脚本顺序调整、或任何人按文档写 `ResumeExport.exportLongImage()`，都会踩空。

修法（零成本）：两边都改成 `Object.assign(global.ResumeExport = global.ResumeExport || {}, { ... })`。

### 4.3 导出逻辑三处重复

- `app.js:537`（`exportJSON`）
- `export-extra.js:53`（`buildBlocks`，DOCX/TXT/MD 共用）
- `export-pdf.js:16`（`makeCaptureClone`，PDF/长图共用）

且 `export-extra.js:357/371` 的 `saveBytes/saveText` 与 `export-pdf.js:109/145` 的 `downloadPDFNow/doExportDownload` 近乎逐行重复。应抽一个公共 `saveBlob()`。

### 4.4 性能：每敲一个键都做全量重渲染 + 强制 reflow

`resume-render.js:349→358` 的 `input` 事件直接调用 `renderPreview()` → `:254` 全量 `preview.innerHTML = 全量 HTML`。编辑器自身不重渲染（这点做对了，保住了光标），但每键还叠加三份额外成本：

1. `RB.saveState()` → `contentHash` → `stableHash`（递归主键排序 + 全量 `JSON.stringify` + 逐字符 djb2）= **O(整份简历)/键**
2. `drawPageGuides()` → `computePageBreaks()` 逐个读 `offsetTop` → **强制同步 reflow**
3. `MutationObserver` + `ResizeObserver` 都挂在同一个 `preview` 上并都触发 `applyPreviewScale()`（读 `clientWidth` + `getComputedStyle`）→ **又一次 reflow**

**全链路没有任何 debounce**（只有写盘有 800ms，见 `app.js:477`；`audit.js:414` 的 600ms 是全项目唯一的节流）。长简历下这是卡顿主因。

### 4.5 其他值得记录的隐患

| 位置 | 问题 |
|---|---|
| `resume-render.js:222/338` | 模块顶层 `const preview = document.getElementById('preview')`，DOM 未就绪则为 `null`，`:262` 立即 `addEventListener` → TypeError，整份脚本挂掉 |
| `serve.js:237/272/310` | 请求体超限后只 `req.destroy()`，不回 413，前端拿不到可用错误 |
| `app.js:284/309/319` | `await ResumeLibrary.list()` 在 `try` **之外** → 失败即未捕获 rejection，用户点了「重命名」毫无反应 |
| `resume-library.js:255/322` | `save()` 与 `remove()` 共享 `_index` 做 read-modify-write，**无串行队列** → index.json 可能丢项 |
| `resume-library.js:121-141` | HTTP 后端一失败就**永久**降级 localStorage，无恢复入口 |
| `resume-render.js:110` | 公司 Logo 未做 scheme 白名单，`data:`/`http:` 会被写进导出的单文件 HTML，形成外链信标 |
| `app.js:406-440` | 用字符串拼内联 `onclick='ResumeEditor.xxx(\''+safeId+'\')'`，而 `esc()` 不转义反斜杠与换行；目前靠服务端正则兜底，浏览器侧无纵深防线 |
| `dist-desktop/js/*.js` | 是 `js/` 的全量**拷贝**，靠 `npm run desktop:assets` 同步，机制上无漂移保护 |

## 五、界面设计诊断

### 5.1 信息架构：同一功能最多出现 4 次，且两端清单不一致

| 功能 | 出现位置 | 问题 |
|---|---|---|
| **导出** | 工具菜单 8 个（`index.html:165-173`）＋ 手机 sync-pane 7 个（`:204-211`）＋ 设置页「导出 JSON」（`settings-view.js:158`） | **手机端缺少「打印/另存为 PDF」与「导出 JSON」**——两端能力不一致 |
| **投递体检** | 工具菜单 `:162` ＋ 编辑面板 `:129` ＋ sync-pane `:196` | 3 处 |
| **主题切换** | 工具菜单 `:163` ＋ sync-pane `:219` ＋ 设置页外观（`:132-147`） | 3 处 |
| **收起编辑面板** | side-rail `:93` ＋ 工具菜单 `:178` | 2 处，且语义重复 |

还有两个**结构性矛盾**：

- **桌面反而少功能**：工具菜单里**没有飞书分组**，「上报/拉取」只存在于手机 sync-pane 与设置页。
- **死入口**：`/portfolio` 已注册（`bootstrap.js:22-23`）但**全 UI 无任何链接**——用户永远到不了。`layout.css:56-81` 里 `route-settings/history/templates/portfolio` 的分支**从不生效**（所有二级页只加 `route-library`）。

### 5.2 桌面端有「藏起来的功能」

左抽屉被 `layout.css:308-311` 在桌面隐藏，于是抽屉里的 **🔔 消息通知、＋新建、上传** 在桌面**全部不可达**。而 `#autosave` / `#feishuStatus` 只存在于 `.side-panel-head`（`index.html:151-152`），该面板默认 `width:0` —— **桌面用户根本看不到保存状态**。

### 5.3 密度问题

右侧编辑面板堆了 5 个 panel；三个 `.font-settings` 各 `max-height:34vh`（`style.css:373`）合计已超一屏，`#panel-audit` 再占 46vh（`:704`）。这是「一次性把所有属性铺开」的思路。

**更专业的方向是检查器（Inspector）范式**：点击预览中的元素 → 右侧只显示该元素的属性。这正是 Figma / InDesign 的做法，能同时解决密度与可发现性。

### 5.4 视觉：单色体系有破口，图标体系缺失

**灰阶破口（硬编码颜色）**：

- `css/ai.css` 整份硬编码 `#fff/#1a1a1a/#666/#999`，且**无 dark 分支** → 夜间模式下 AI 面板仍是白底
- `layout.css:238 #3370ff`、`:279 #ff6b6b`、`:1188 #e5484d`、`:1251-1254` 通知四色、`:1163 #2e9e44`
- `style.css:516 .dl #2e8b57`
- `tracker-view.js:18-26` 投递状态色内联（蓝/紫/绿/红）

**图标体系缺失**：rail 用 `▦ ✎ ▤ ☰ ✦ ⚙` 等几何字符（`layout.js:22-42`，语义弱、字体依赖），铃铛是真 emoji `🔔`，空态用 `📄 🏷`。**没有任何 SVG 图标**。

**层次仅两级**（13px 粗 / 11.5px 灰），信息分组靠留白硬撑。

### 5.5 做得好的地方（应保留）

空状态处理是亮点：`.list-empty`、`.lib-empty`、`.pf-empty`、`.resume-drawer-empty`、`.spinner` 齐备，文案也写得清楚（「从一份空白简历开始，或导入已有的 PDF / JSON」）。`@media print`（`style.css:525-557`）主体完整，有强制白纸与 `break-inside:avoid`。

## 六、交互设计诊断

### 6.1 撤销栈的三处问题

1. **跨简历污染**：快照是 `{data,fonts,spacing}`（`app.js:20`），**切换简历不清栈** → 在 A 简历里按 Ctrl+Z 可能把 B 简历的内容改回去。
2. **吃掉输入框原生撤销**：`app.js:116` 全局 `preventDefault` → 在文本框里想撤一个词，会**回滚整份简历**。
3. **撤销后不落盘**：`undo()`（`:41-47`）不调 `markDirty/saveState`，撤销结果可能不写盘。

### 6.2 保存反馈是最大的信任缺口

`showAutosave()`（`app.js:528`）文案写「✓ 已自动保存 · 时:分:秒」，但：

- 容器默认收起（在宽度为 0 的面板里）
- 手机端 `display:none`
- 800ms 防抖期内**没有「保存中」状态**
- **写盘失败被 `try{}catch{}` 吞掉**（`:470`），用户永远不知道

未保存标记只是一个 `●` 前缀加在抽屉标题上（`:441`）——桌面同样看不到。

> 一个编辑器最基础的能力是「让我知道我的东西安全吗」。这是当前**性价比最高的一个改动**。

### 6.3 误操作与可发现性

- **拖拽**只有 `cursor:grab`（`style.css:441/449/476`），无把手、无首次引导；跨类型拖拽**静默失败**（`resume-render.js:274-281`）；触屏**完全不可用**（HTML5 DnD 在移动端不支持）
- **28 处 `alert/confirm/prompt`**，全项目**没有 toast**；体检结果直接弹一整段文本（`audit.js:434`）
- **div 当按钮**：`.lib-card`（`library-view.js:191`）无 `tabindex/role`，键盘不可达；`⋯` 菜单（`app.js:399-421`）无 `aria-expanded`、无焦点管理
- **面板互斥有漏洞**：side-panel 与编辑面板互斥（`pane-mobile.js:22-24`），但 **AI 面板不受约束**（`ai.css:4` fixed / z-index 300）会叠加上去

### 6.4 可访问性

- **无全局 `:focus-visible`**：仅输入框与 `⋯` 一处有焦点样式，**按钮零焦点环**
- **断点只有 640 / 641–1024**（`style.css:646`），手机隐藏 `.side-rail,.side-panel`（`:578`）→ **撤销/重做、分页线、文件名在手机上彻底消失**
- **对比度不达标**：`--ui-faint #9a9a9a` 用于 11px 元信息（`.resume-item-meta:306`、`.lib-filter-n:805` 还叠 `opacity:.6`）≈ **2.8:1**
- **字号下限过低**：字号配置最小 **8px**（`data.js:32/36/37/38`）→ 可以产出 8px 正文的简历
- ARIA 全项目约 10 处；`pdf-modal`/`tk-modal` 无 `role=dialog`/`aria-modal`/焦点陷阱

## 七、发展方向：从「编辑/分发基础设施」转向「内容生产与投递闭环」

### 7.1 一个必须先说清的事实

从 `git log` 与目录状态看，近期的工程投入集中在：**Tauri 跨平台壳（4 平台）→ CI 三平台矩阵 → Android 签名 → 飞书 OAuth → 设备流扫码注册 → 多数据源抽象 → 多页面路由 → 消息通知中心 → 投递追踪**。

但真实使用形态是：**浏览器版 + 旧的单份 `data/resume.json`**。

```
~/Library/Application Support/com.resumestudio.desktop/   ← 不存在
```

也就是说，**桌面版从未被真正使用过**，飞书同步、多简历库、投递追踪都还是「建好了但没住人」的状态。

同时，工作区目录名是 `简历定制优化` —— 这透露了真实意图：**针对某个岗位 JD 定制并优化简历**。而当前产品里，**没有任何一处是为这个场景服务的**。

### 7.2 定位建议

简历工具的护城河**不在编辑器，在内容**。用户真实痛点排序：

| 排序 | 痛点 | 当前覆盖 |
|---|---|---|
| 1 | **我该写什么、怎么写才有竞争力** | ❌ 完全没有 |
| 2 | **这份简历能过这个 JD 的筛吗** | ⚠️ 只有通用规则体检，不看 JD |
| 3 | 排得好看吗、能过 ATS 吗 | ✅ 做得很好 |
| 4 | 存哪儿、手机能看吗 | ✅ 做得很好（但没人用） |

**建议把重心从 3/4 挪到 1/2。** 排版与分发基础设施已经足够好，继续加码的边际收益很低；而内容生产是零覆盖、且是用户真正的付费/使用理由。

### 7.3 三条演进主线

**主线 A：JD 驱动的「一岗一简历」**（最高优先级，直接对应目录名意图）

1. ✅ 粘贴 JD → 解析出关键词/硬技能/职责词（已落地：`js/jd-match.js`）
2. ✅ 与简历内容做匹配度分析：**已覆盖 / 弱覆盖 / 缺失**，并标出命中板块（已落地，见 §十进度）
3. 生成针对该 JD 的**派生版本**（不覆盖主简历），投递后记录在案 ← **下一步**
4. ✅ 复用已有 `js/audit.js` 的规则骨架与灰阶视觉词汇，成本可控

**主线 B：内容质量闭环（AI 辅助）**

仓库里已有完整设计方案（`docs/AI辅助写简历-技术设计方案.md`）与阶段 1 基建（`tools/ai-proxy.js` + `js/ai/*`）。阶段 2 的核心闭环（选中 → 润色 → Diff → 应用 → 撤销）**尚未实施**，这正是把「痛点 1」变成功能的那一步。

关键原则（设计文档已定，应坚持）：**AI 永不直接落笔，必经 Diff 审阅；作用范围显式；进撤销栈；事实护栏拦截编造的数字与公司名；可脱敏再发送。**

**主线 C：投递闭环打通**

`#/tracker` 现在是个孤岛（localStorage CRUD，与简历库无关联）。应该做成：**简历版本 ←→ JD ←→ 投递记录 ←→ 结果反馈**。价值在于形成「哪种写法拿到了面试」的反馈回路——这才是真正无法被替代的数据资产。

## 九、不建议做的事

1. **不要在 AI 之前继续加导出格式或新平台。** 导出已有 6 种、平台已有 4 个，边际收益已经很低。
2. **不要引入框架或打包器。** 项目已明确决策不上 React/Vue/Vite（守 `file://` 直开 + 单文件离线版）。上面所有建议都用原生 CSS/JS 可完成。
3. **不要做服务端账号体系。** 已否决，且没必要——数据可移植性由 JSON 导入导出覆盖。
4. **不要再加顶层面板/页面。** 已有 7 个 view，其中 2 个是空壳/无入口。下一步应该是**收敛**而不是扩张。
5. **不要把「桌面版没人用」简单理解为「需要推广」**——更可能是「浏览器版已经够了」。可以先问：桌面版真正不可替代的能力是什么（离线？凭证保管？）。如果答案是「和浏览器差不多」，那它就不该继续吃维护成本。
