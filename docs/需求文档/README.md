## 明确不做（防止被竞品带偏，延续既有决策）

1. **不引入 React/Vue/NestJS/Next.js 框架**——三家全是框架型，但本项目「原生 JS + file:// 直开 + 单文件离线版」是护城河，架构层面一律不抄。
2. **不做服务端账号体系 / 不自托管后端**——Reactive Resume 的 NestJS 自托管栈不学；分享靠静态 HTML 即可。
3. **不引入 react-pdf / 客户端 PDF 引擎**——与「自由 CSS 排版」护城河冲突（纯前端矢量 PDF 要放弃自定义 CSS）。
4. **不学 RenderCV/LapisCV 的 CLI/LaTeX/YAML 路线**——违背可视化编辑定位（借鉴其「简历即代码 + Git 版本控制」哲学，本项目已用「分文件 + 飞书版本历史」实现）。
5. **不在 AI 之前继续加导出格式或新平台**——导出已有 6 种、平台 4 个。
6. **不做 Editor 级协作分享权限**——需协作后端，与零后端决策冲突。

## 需求文档编写规范

每篇需求文档遵循统一结构，方便开发认领：

```
# <需求名>
> 编号 / 优先级 / 借鉴来源 / 状态 / 评审结论

## 一、背景与竞品参照
## 二、用户价值（痛点 → 收益）
## 三、需求描述（功能点 + 交互细节，含边界与异常）
## 四、数据结构（如涉及存储/schema 变更）
## 五、验收标准（可测试的量化指标）
## 六、工程护栏（项目铁律 + 测试要求）
## 七、非目标（明确不做的范围）
## 八、评审结论（护城河/价值/成本/依赖四问 + 通过/降级/否决）
```
