# 产品定位与评审标尺

> 本文是需求评审的**标尺**：所有需求的取舍，都回到「是否符合本项目护城河、是否对齐真实使用形态」来评判。
> 维护：产品定位变化时更新本文，并同步调整各需求文档的「借鉴合理性」结论。

---

## 一、本项目是什么（一句话定位）

**一份「数据可自持、可跨端」的简历排版 + 投递工具**：把「自由 CSS 排版」做到极致，守住「数据自己掌控、不依赖服务端账号」，再用 AI 补上「内容生产」的短板。

---

## 二、六大护城河（评审时逐条对照，守住不丢）

| # | 护城河 | 含义 | 竞品谁没有 |
|---|---|---|---|
| 1 | **自由 CSS 排版引擎** | 用户可颠覆传统布局、自由排版（字号/间距/引用线/强制换页/板块增删），导出与预览同源 | 所有框架型竞品（react-pdf 放弃自由 CSS） |
| 2 | **原生 JS + file:// 直开** | 无打包器、无框架，双击即开，断网可用 | 三家主流竞品全是 Next.js/React 框架 |
| 3 | **单文件离线 HTML** | 一份简历 = 一个可分享的离线 HTML | 无 |
| 4 | **数据自持（分文件模型 + JSON 可移植）** | 一份简历一个文件，可 git 管理、可导出导入迁移，不做账号体系 | Reactive Resume 数据锁在数据库 |
| 5 | **飞书同步 + 版本历史** | 借飞书文档/云盘留存每次更改，天然版本控制 | 无（竞品要么无同步、要么自建账号） |
| 6 | **Tauri 桌面 / 安卓壳** | 免装 Node，原生层保管凭证 | 无（竞品多为 Web/Docker） |

---

## 三、真实使用形态（决定需求优先级的事实依据）

据 `docs/产品与竞品分析/产品评估与演进建议.md` 结论：

> 真实用法是「**本地浏览器编一份简历**」；桌面版/飞书同步/多简历库属「建好没住人」；产品重心应转向 **JD 驱动的「一岗一简历」**。

由此推导的优先级原则：

1. **内容生产（AI/JD 定制）> 排版美化**——用户最痛是"写什么"，不是"怎么排"（排版已是护城河）。
2. **投递闭环（求职信/追踪）> 更多导出格式**——导出已有 6 种，边际收益低。
3. **中文场景翻译/求职信 > 界面 i18n**——用户是中文求职者，跨语言是简历内容的翻译，不是界面按钮的中英文。

---

## 四、评审四问（每个需求都要过一遍）

1. **护城河**：是否守住六大护城河？是否被竞品带偏（引框架/做账号/放弃自由 CSS）？
2. **价值**：是否对齐「JD 驱动一岗一简历」的产品主线？
3. **成本**：是否纯增量、低风险？还是牵动核心渲染/存储的破坏性改动？
4. **依赖**：是否依赖其他未完成需求或前置条件（如 API Key）？

---

## 五、明确不做（评审红线，踩中即否决/降级）

1. 不引 React/Vue/NestJS/Next.js 框架。
2. 不做服务端账号体系 / 不自托管后端。
3. 不引 react-pdf / 客户端 PDF 引擎（放弃自由 CSS）。
4. 不学 RenderCV/LapisCV 的 CLI/LaTeX/YAML 路线（违背可视化编辑定位，但借鉴其「简历即代码 + Git 版本控制」哲学）。
5. 不在 AI 之前继续加导出格式或新平台。
