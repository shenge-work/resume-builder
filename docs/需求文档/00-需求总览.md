# 00 需求总览

> 本文件是 `docs/需求文档/` 的**总入口**，回答三个问题：
> 1. **先后顺序**是什么（开发路径图 + 依赖关系）；
> 2. 哪些需求**已完成归档**；
> 3. 哪些需求**待评审**、哪些**待开发**。
>
> 评审标尺见 **[00-产品定位与评审标尺](./00-产品定位与评审标尺.md)**（护城河/价值/成本/依赖四问）。
>
> 维护规则：需求状态流转 `待评审 → 待开发 → 开发中 → 待验收 → 已完成（归档）`。每篇需求文档的状态字段以此为准，与本文件保持一致。

---

## 一、状态定义与流转

```
待评审（刚提出，需评审确认范围/优先级）
   │  评审通过
   ▼
待开发（评审通过，等排期认领）
   │  认领开工
   ▼
开发中
   │  开发完成
   ▼
待验收（等验收标准逐条核对）
   │  验收通过
   ▼
已完成 ──► 归档（移出活跃列表，保留需求文档作基线）
```

> ⚠️ 已完成需求**不删除文档**，仅从「活跃需求」移到「归档」分区。

## 五、评审操作指引

新需求进入评审列表时，需回答以下问题（写进需求文档开头的「评审结论」区块）：

1. **范围**：这个需求到底做不做？做多少？
2. **优先级**：P1/P2/P3，以及理由（价值 × 成本 × 依赖）。
3. **借鉴合理性**：是否符合本项目「原生 JS + file:// 直开 + 自由 CSS」护城河？是否落入「明确不做」清单？
4. **依赖**：是否依赖其他未完成需求？
5. **验收标准**：验收标准是否可量化、可测试？
6. **负责人/排期**：谁来开发？预计什么时候完成？

评审通过后，把该需求从「待评审」移到「待开发」，并更新需求文档状态字段。

## 六、明确不做（防止被竞品带偏，延续既有决策）

1. **不引入 React/Vue/NestJS/Next.js 框架**——架构护城河。
2. **不做服务端账号体系 / 不自托管后端**——分享靠静态 HTML。
3. **不引入 react-pdf / 客户端 PDF 引擎**——与自由 CSS 护城河冲突。
4. **不学 RenderCV/LapisCV 的 CLI/LaTeX/YAML 路线**——违背可视化编辑定位（借鉴其「简历即代码 + Git 版本控制」哲学即可，本项目已用「分文件 + 飞书版本历史」实现）。
5. **不在 AI 之前继续加导出格式或新平台**。
6. **不做** Editor 级协作分享权限（需协作后端，与零后端冲突）。

## 七、评审纪要（2026-09-21，产品经理评审）

本次以产品经理视角，对照 [00-产品定位与评审标尺](./00-产品定位与评审标尺.md)，对全部需求做了一次评审 + 竞品补充调研（新增 Magic Resume、Magic Self、Hirable、RenderCV/LapisCV 等参照）。主要结论：

1. **补了 3 个竞品驱动的缺口**：
   - **N7 求职信与面试准备**（Resume Matcher 核心闭环，原 N2 遗漏立项）；
   - **N8 简历内容翻译**（Magic Resume 一键翻译，中文求职者刚需）；
   - **N9 个人求职官网导出**（Magic Self 方向，ROADMAP 已设计但需求文档缺失）。
2. **补了 1 个已落地基线**：**D6 投递追踪**（Hirable 核心能力，本项目 #/tracker 已落地）。
3. **吸收竞品设计精华**：N1 吸收 Magic Resume 19 套模板的「完全自定义」；N3 吸收 Magic Resume 三级分享权限（Viewer/Commenter/Editor，Editor 列 P3 未来方向）。
4. **优先级重新校准**（对齐「JD 驱动一岗一简历」主线）：
   - N5 缩略图 P2→**P3**（价值偏低）；
   - N6 导出引导确认 P3（成本极低可搭车）；
   - N7/N8 与 N2 **共享 AI 基建**，建议三者同期排期（省一半）。
5. **澄清边界**：N4 是「界面 i18n」，N8 是「简历内容翻译」，两者独立（原 N4 标题「多语言」有歧义）。
