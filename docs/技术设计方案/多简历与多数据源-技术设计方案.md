# 多简历 & 多数据源 · 技术设计方案

> 状态：📋 **规划中 · 待实施**
>
> 本文设计「一份编辑器管理多份简历」「以免费云笔记平台（飞书 / 腾讯文档 / 金山文档 / ima 等）
> 作为数据源」的演进方向，以及「**发版引导 / 更新说明**」机制（新包装好后首启弹引导）。
> 当前代码库仍为**单份简历**（`data/resume.json` 单文件 + 飞书双写单文件）。
>
> 核心诉求（来自产品定位）：**数据源不需要用户自己采购 OSS、搭数据库、买服务器**，
> 用通用免费的云笔记平台的开放 API / 机器人 / CLI 能力托管简历数据。

---

## 0. 一条贯穿始终的判断

这些云笔记平台本质是「**面向人的文档 / 文件存储**」，不是「面向程序的 KV 数据库」。
因此**数据源适配器不能假设有 `put(key, json)` 这类结构化写入能力**，而必须统一抽象成「**文档读写**」：

> 每份简历 = 一个「文档 / 文件」，适配器负责在各自平台里找到它、读它、写它；
> 平台没有的能力（如 ima 无可编程写入）就声明为「不支持」，由 UI 自动降级。

这是整个架构的根基，决定了「多简历」与「多数据源」是一件事的两面：
**多简历 = 一个平台里存多个文档；多数据源 = 同一份简历可以落到不同平台的文档。**

## 1. 架构总览

```
┌─ UI 层 ─────────────────────────────────────────────┐
│  简历抽屉（列表/新建/切换） · 顶部标签页（多开编辑） · 数据源连接面板 │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─ 核心抽象层（新增）───────────────────────────────────┐
│  ResumeLibrary        多份简历的元数据 + 当前激活项      │
│  DataSourceAdapter    统一接口 + 能力声明，可插拔扩展     │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─ 数据源实现层（按能力适配）─────────────────────────────┐
│  本地 IndexedDB ｜ 飞书 ｜ 腾讯文档 ｜ 金山 WPS ｜ ima(仅导出) │
└──────────────────────────────────────────────────────┘
```

与现有 `ResumeStore`（`js/store/resume-store.js`）的关系：
`ResumeStore` 是「**单份简历**的读写门面」，本次在其**之上**新增一层 `ResumeLibrary`，
负责「多份」的编排；`ResumeStore` 的 `LocalStore / BrowserStore / FeishuStore` 被
`DataSourceAdapter` 逐步收编为「适配器」实现。**对外接口不破坏，UI 从单份平滑过渡到多份。**

## 2. 数据源结构设计（地基）

### 2.1 「索引清单」与「简历文档」分离

多简历**不塞进一个大 JSON**，而是两级结构：

**① 索引清单**（体积小、频繁读写，存在每个数据源的「根位置」）：

```jsonc
{
  "version": 1,
  "resumes": [
    { "id": "res_8f3a", "title": "林一帆 · Agent 岗",  "updatedAt": 1758..., "source": "feishu",    "docId": "docx_xxx" },
    { "id": "res_9c21", "title": "林一帆 · 后端岗",  "updatedAt": 1758..., "source": "local",     "docId": null },
    { "id": "res_a11b", "title": "通用版（未定向）", "updatedAt": 1758..., "source": "tencent",   "docId": "file_yyy" }
  ],
  "activeResumeId": "res_8f3a"
}
```

**② 每份简历 = 一个独立文档**，内容就是现在的 `{ data, fonts, spacing, v }` 结构（**完全不变**）。

**为什么分离（而非一个大数组）：**

| 理由 | 说明 |
|---|---|
| 单份已很大 | 含 logo base64、技能组、项目等，塞一起会让「切换」变成「加载全部」，移动端卡死 |
| 版本历史按简历隔离 | 改 A 简历不该污染 B 简历的飞书版本历史 |
| 冲突合并按简历隔离 | 多端同时改不同简历时互不干扰 |
| 部分加载 | 打开时才拉取该简历的完整内容，列表只读索引 |

### 2.2 `ResumeLibrary`（简历仓库，纯 JS，跨端通用）

```js
const ResumeLibrary = {
  // 生命周期
  async init(),                              // 启动：读索引清单，恢复 activeResumeId
  // 简历 CRUD
  async list(),                              // → 索引数组（标题/来源/更新时间，不含正文）
  async create({ title, fromResumeId }),     // 新建（可基于某份复制）
  async rename(id, title),
  async duplicate(id),
  async remove(id),
  // 打开 / 切换（多开的关键）
  async open(id),                            // 加载完整 payload 进工作区
  async switchTo(id),                        // 切激活态（移动端 = 保存当前再切）
  async save(id, payload),                   // 写回本地 + 触发远端同步
  async getActive(), setActive(id),
  // 远端同步（委托给 DataSourceAdapter）
  async pull(id), async push(id),
  async listVersions(id), async restore(id, versionId)
};
```

要点：
- 库本身**不直接碰任何平台**，全部委托给 `DataSourceAdapter`。
- 每份简历独立持有撤销栈（`recordHistory` 按简历 id 分桶）。
- 索引清单也走数据源（存远端），实现「换设备还能看到我的简历列表」。

### 2.3 `DataSourceAdapter`（可插拔适配器接口）

```js
const DataSourceAdapter = {
  id: 'feishu',                 // 唯一标识
  displayName: '飞书',
  capabilities: {               // ★ 能力声明 —— 降级的关键
    list: true,      // 能否列出该平台的文档
    read: true,      // 能否读取
    write: true,     // 能否可编程写入
    versions: true,  // 是否有版本历史
    oauth: 'app'     // 授权方式：'app'（自建应用）| 'oauth'（扫码）| 'none'
  },
  // 统一操作（返回 null 或抛「不支持」→ UI 触发降级）
  async listDocuments(),                       // → [{docId, title, updatedAt}]
  async readDocument(docId),                   // → {data,fonts,spacing,v}
  async writeDocument(docId, payload),         // → {versionId}
  async listVersions(docId),                   // → [{versionId, time, size}]
  async restoreVersion(docId, versionId),
  async exportMarkdown(payload),               // → 供 ima 等「手动粘贴」平台用
  // 绑定 / 授权
  async authorize(ctx),                        // 触发扫码/授权流程
  async loadConfig(), async saveConfig(cfg)
};
```

**能力声明驱动 UI（不是写死 if-else）**：UI 根据 `capabilities` 决定显示哪些按钮。
例：ima 只能 `read`（手动粘贴）→ **不显示**「自动保存到 ima」，只显示「导出为文本手动粘贴」。

### 2.4 多源并存的存储策略

**「本地为锚 + 一个主远端 + 可选备份远端」**：

- **本地 IndexedDB**：永远可用、零门槛，所有编辑先落本地（锚点）。
- **主远端**（默认飞书）：自动同步、版本历史、跨设备。
- **备份远端**（可选）：手动「另存到腾讯文档」等，第二份保险。

用户一个云平台都没绑，产品也能用（纯本地）——符合「不强制用户采购任何东西」的定位。

### 2.5 各平台真实能力预期（当前调研，接之前需复核官方文档）

| 平台 | list | read | write | versions | 授权 | 落点 |
|---|---|---|---|---|---|---|
| 飞书 | ✅ | ✅ | ✅ | ✅ | app / oauth | **主数据源** |
| 腾讯文档 | 🟡 需资质 | ✅ | 🟡 | ❌ | oauth | 备份源 |
| 金山 WPS | 🟡 | ✅ | 🟡 | ❌ | oauth | 备份源 |
| ima | ❌ | ✅(手动) | ❌ | ❌ | 无 | 仅手动导入/导出 |
| 本地 | ✅ | ✅ | ✅ | 快照 | 无 | 锚点 |

> ⚠️ ima 目前**无公开可编程 API / 机器人 / CLI**，当不了自动存储，只能作「导出目标」。
> 腾讯文档 / 金山的 API 有资质门槛，接入前需先完成开发者认证；`🟡` 项以官方最新文档为准。

## 3. 界面交互设计（多简历）

### 3.1 双轨交互模型

| 区域 | 职责 | 类比 |
|---|---|---|
| **左抽屉（简历列表）** | 新建 / 重命名 / 复制 / 删除；看每份简历「存在哪、多久前更新」 | 文件管理器 |
| **顶部标签页（已打开工作区）** | 多份简历同时打开、并行编辑 | 浏览器标签 |

两者缺一不可：只有抽屉 → 切换要整份重载、无法「开着 A 参考 B」；只有标签 → 简历一多标签爆炸、无管理入口。

### 3.2 关键交互细节

| 交互 | 设计 |
|---|---|
| 切换简历 | 点抽屉条目 → 已打开则跳到该标签，否则新开标签 |
| 同时编辑 | 每个标签 = 独立编辑器实例（独立预览 + 编辑面板），独立撤销栈 |
| 未保存标记 | 标签名后 `●` 提示该份有未同步修改 |
| 防误关 | 关闭含未同步内容的标签时弹「保存 / 丢弃」确认 |
| 快捷键 | `⌘1~9` 切第 N 标签；`⌘N` 新建；`⌘⇧[` / `⌘⇧]` 切上/下标签 |
| 移动端 | 抽屉全屏化；标签变底部横向滑动条（单开策略，见下） |

### 3.3 桌面多开 vs 移动单开（已定）

- **桌面**：标签页多开（像浏览器）。
- **移动端**：**单开**——点另一份简历即切换，切换前自动保存当前份。
  （多开在移动端屏幕小、体验必然打折，成本高收益低，暂不做。）

## 4. 飞书「一键绑定」与默认配置自动填入

### 4.1 路线选择（已定：先做「简化配置」）

| 路线 | 说明 | 状态 |
|---|---|---|
| **A. 简化配置**（本次实施） | 粘贴一次 app 凭证 → 后端自动探测并回填所有默认项 | ✅ 选定 |
| B. 真·扫码 OAuth | 扫二维码授权，用户不碰 key；**仅原生壳可做**（浏览器无稳定回调域名） | 后续 |

> 「扫码」之所以有前提：飞书自建应用（app_id/secret）本身是「管理员后台装应用」，不是 OAuth 扫码；
> 真·扫码对应 OAuth 授权码模式，需要回调地址 + 能收 token 的客户端，纯浏览器模式（`npm start`）走不通，
> 只能在 Tauri 原生壳里做。故先做 A，把配置从「填 6 项」降到「填 1 项」，零风险、全端可用。

### 4.2 简化配置交互流程

```
用户点「绑定飞书」
  → 只填 app_id + app_secret（仅此 2 项，其余全部自动）
  → 点「自动探测并绑定」
  → 后端（feishu-sync.js 增强）：
      1) 换 tenant_access_token 验证凭证
      2) 自动探测 domain（feishu.cn / larksuite.com）
      3) 自动创建默认文件夹「简历数据」，回填 folder_token
      4) 回填 doc_title = 简历数据备份、file_name = resume.json
      5) 回填 fileUploadMode = versioned
  → 前端显示「已绑定 ✓ 账号 xx」+ 各默认项（可手动改）
  → 凭证只存服务端 / OS 钥匙串，永不进浏览器
```

### 4.3 默认配置自动填入清单

| 配置项 | 自动默认值 | 说明 |
|---|---|---|
| `domain` | `feishu.cn` | 自动探测 |
| `folder_token` | 自动创建「简历数据」文件夹 | 首次绑定自动建 |
| `doc_title` | `简历数据备份` | 可改 |
| `file_name` | `resume.json` | 可改 |
| `fileUploadMode` | `versioned` | 默认版本化上传 |

### 4.4 （后续）真·扫码 OAuth 实现要点

```
点「绑定飞书」→ 原生壳打开飞书授权页 → 手机扫码 → 授权
→ 飞书回调 code → 原生壳用 app_id/secret 换 access_token → 存 OS 钥匙串
→ 前端显示「已绑定」→ 自动创建默认文件夹/文档
```

`app_secret` 只在原生层，延续「凭证不进浏览器」红线。

## 5. 扩展接口：如何优雅接金山 / 腾讯 / ima

**注册新数据源只需一件事**：实现适配器 + 声明能力，UI 与仓库层零改动。

```js
ResumeDataSourceRegistry.register({
  id: 'tencent-doc',
  displayName: '腾讯文档',
  adapter: TencentDocAdapter,
  capabilities: { list: true, read: true, write: true, versions: false, oauth: 'oauth' }
});
```

- **飞书** = 现有 `tools/feishu-sync.js` 逻辑平移进适配器（主数据源，能力最全）。
- **腾讯文档 / 金山** = 按各自开放 API 实现 `listDocuments / readDocument / writeDocument`，声明 `versions:false` → UI 自动隐藏「版本历史」入口。
- **ima** = 声明 `{ export:true }`，走 `exportMarkdown`，UI 只显示「导出为文本手动粘贴」。
- **统一协调器** `Coordinator`：打开即 `pull` 索引 → 编辑防抖 `push` → 冲突走字段级 3-way merge（沿用跨平台设计 P4 思路，按简历 id 隔离）。

## 6. 发版引导 & 更新说明（onboarding / changelog）

> 背景：项目已多端适配（浏览器 / 桌面 Tauri / 安卓），未来会持续发新包。诉求——
> **用户装完新包第一次打开时，弹引导页告知「这次更新了什么、怎么用」**，且不重复打扰。

### 6.1 现状问题（设计的事实基础）

| 项 | 现状 | 问题 |
|---|---|---|
| 产品版本号 | 分散三处且**不一致**：`package.json`=`1.0.0`、`Cargo.toml`+`tauri.conf.json`=`0.1.0` | 没有单一版本源，「当前什么版本」说不清 |
| 数据 schema 版本 | `js/app.js` `SAVE_VERSION = 8` | 这是**数据格式版本**（驱动迁移），与「产品版本」是两回事，**不能混用** |
| 引导层 | 无 | `bootDone` 之后直接进编辑器，没有 onboarding / 更新说明 |

### 6.2 核心设计：单一版本源 + 版本比对触发

**① 统一产品版本号（发版只改一处）**

新增单一版本源 `VERSION`（如 `1.2.0`），发版时只改这里，其余自动同步：

```
VERSION（单一来源，可放 package.json 或独立 version.json）
   ├─ 构建期注入前端 → window.__APP_VERSION__（引导页比对用）
   ├─ 同步 Cargo.toml / tauri.conf.json 的 version（Tauri 打包元数据）
   └─ 写入产物文件名（Resume-Studio-1.2.0.dmg 等）
```

消除现在「三处版本不一致」的隐患。用构建脚本（`tools/bump-version.js` 之类）一次性同步，
避免手改多处。

**② 更新说明随包分发（离线可用，不依赖联网）**

引导页内容不能联网拉取（用户可能离线 / 内网），必须**打进安装包**：

```
CHANGELOG.md（Keep a Changelog 格式，人读）
        │  构建脚本抽取
        ▼
release-notes.json（随包分发，机器读）
{
  "version": "1.2.0",
  "date": "2026-09-20",
  "items": [
    { "type": "feature",  "title": "多简历管理",     "detail": "左侧抽屉可新建/切换/复制简历", "guide": "点左上角「简历」图标" },
    { "type": "fix",      "title": "修复打印边距",   "detail": "…" },
    { "type": "breaking", "title": "数据源改为多源", "detail": "…", "guide": "…" }
  ]
}
```

`type` 取值 `feature / fix / breaking / guide`，驱动引导页的视觉分组（黑白灰下靠「标记前缀 + 字重」区分，
如 `新功能` / `修复` / `重要变更`）。

**③ 触发判定：比对「上次已看版本」**

```
启动 → 读本地 seenVersion（无 = 全新安装）
  ├─ seenVersion 为空        → 全新安装：显示「欢迎引导」（产品介绍 + 三步上手）
  ├─ seenVersion < 当前版本   → 升级：显示「更新说明」（本次改了什么 + 怎么用）
  ├─ seenVersion ≥ 当前版本   → 正常进入（降级/回滚/重开都不打扰）
  └─ 用户看完点「开始使用」    → 写 seenVersion = 当前版本，下次不再弹
```

- `seenVersion` 存 localStorage（浏览器）/ 应用数据目录或钥匙串（原生壳）。
- **版本比较用 semver**（`1.10.0 > 1.9.0`），不能字符串比较，否则 `1.10.0 < 1.9.0` 会误判。

### 6.3 引导页交互规范（严格黑白灰）

| 形态 | 内容 |
|---|---|
| **全新安装** | 欢迎页（产品名 + 一句话定位）+ 3–5 步上手（预览/编辑 → 数据源/飞书绑定 → 导出 PDF）+「开始使用」 |
| **升级** | 标题「更新到 v1.2.0」+ 按 `feature/fix/breaking` 分组的更新条目 + 关键新功能「怎么用」指引 +「知道了」 |

- 一次只讲一件事，分页或滚动；「跳过」和「完成」都写 `seenVersion`（不强迫看完）。
- 引导页用 `--ui-*` 灰阶变量，**不引入新颜色**；`@media print` 隐藏（不进 PDF）。
- 「更新说明」之后可在工具栏「关于 / 更新日志」里**随时回看**（读同一份 release-notes.json），
  不只首启一次可见。

### 6.4 与现有架构的衔接

- **浏览器版 / 单文件版**：也读 `release-notes.json`，但「引导」降级为「顶部一条可关闭的更新提示条」
  （浏览器没有「安装」概念，每次刷新都弹整页引导会烦）。**只有桌面/安卓壳走整页引导。**
- **多端版本不一致**：`seenVersion` 按端独立存储（桌面和手机各自的引导不互相影响）。
- **原生壳**：版本号从 `tauri.conf.json` 读取，前端经 `window.__APP_VERSION__` 或 `__TAURI__.app.getVersion()`
  拿到，与 release-notes.json 的 `version` 比对。

### 6.5 新增产物与改动点

| 产物 | 说明 |
|---|---|
| `tools/bump-version.js` | 发版脚本：读单一版本源 → 同步 Cargo/tauri.conf/package.json → 抽取 CHANGELOG → 生成 release-notes.json |
| `release-notes.json` | 随包分发的结构化更新说明（构建脚本注入 `dist-desktop/` 与单文件版） |
| `js/release-notes.js` | 引导页逻辑（比对 seenVersion → 渲染引导 / 更新说明 → 写 seenVersion） |
| `index.html` | 加引导页容器 + `release-notes.js` 脚本 + 工具栏「更新日志」入口 |
| 构建脚本白名单 | `build-desktop-frontend.js` / `build-single.js` 补 `release-notes.json` 与 `js/release-notes.js` |

## 7. 分阶段路线（每步可停、可验收）

| 阶段 | 内容 | 价值 | 估时 |
|---|---|---|---|
| **M1 多简历数据模型** | `ResumeLibrary` + 「索引清单 + 独立文档」+ IndexedDB 存储 | 单份 → 多份地基 | 2-3 天 |
| **M2 多简历 UI（桌面）** | 左抽屉 + 顶部标签 + 切换/新建/复制/删除 | 核心交互可见，纯浏览器可验 | 2-3 天 |
| **M3 飞书一键绑定** | 简化配置表单 + 自动探测/自动建默认项 | 飞书配置从 6 项降到 1 项 | 1-2 天 |
| **M4 数据源适配器抽象** | 飞书逻辑重构成 `DataSourceAdapter` + 能力声明 | 为金山/腾讯铺路 | 2-3 天 |
| **M5 第一个新数据源** | 接腾讯文档（或金山）验证可插拔 | 证明「可插拔」成立 | 2-3 天 |
| **M6 移动端多简历** | 抽屉全屏化 + 底部滑动标签 + 单开策略 | 移动端体验闭环 | 2-3 天 |
| **M7 发版引导** | 版本号统一 + release-notes.json + 首启引导页 | 用户装新包看懂更新 | 1-2 天 |
| **（后续）OAuth 扫码** | 原生壳里做真·扫码 | 面向公众分发时才需要 | 3-5 天 |

**推荐顺序**：M1 + M2（纯浏览器可验）→ M3（飞书变简单）→ **M7（发版引导）**，
因为 M7 依赖「版本号统一」，而版本号统一是发第一个正式包的前置；M4–M6 与多数据源强相关，
可并行或排后。

每阶段保持 `npm test` 与 `npm run build` 通过。

## 8. 待办 / 待确认

1. **腾讯文档 / 金山 API 的资质门槛**：个人开发者能否顺利拿到开放 API 权限，接入 M5 前需先实测确认。
2. **ima 是否有隐藏能力**：若后续 ima 开放 API/CLI，可把它的 `capabilities` 从 `{export}` 升级为 `{read,write}`，接口无需改。
3. **移动端单开的「自动保存」语义**：切换前自动保存是「保存到本地」还是「也推送到远端」，需在 M6 定。
4. **索引清单的远端存储位置**：飞书用「云盘某固定文件」，腾讯/金山各有约定，需在每个适配器里定义「根位置」。
5. **发版引导的版本比较**：需引入 semver 比较（零依赖自实现即可），避免 `1.10.0 < 1.9.0` 的字符串比较误判。
6. **引导页「是否强制看完」**：默认「可跳过、跳过也记已读」；若某版本有 breaking change 需强制确认，可用 `release-notes.json` 里的 `blocking:true` 标记。
