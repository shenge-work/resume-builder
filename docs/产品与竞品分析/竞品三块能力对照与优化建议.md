# 竞品三块能力对照与优化建议

> 日期：2026-09-21　依据：上一会话《竞品结论回顾》三大高星项目（Reactive Resume ★43.2k / Resume Matcher ★28.5k / OpenResume ★8.9k）的**具体实现细节**（本次补充调研到代码级），对照本项目现状，逐块判断「能否借鉴、值不值得改、怎么改」。
> 范围：仅限用户指定的三块 —— **① 简历导出（PDF/图片）② 简历编辑区 ③ 多简历托管与存储结构**。

---

## 〇、一句话结论

三块里，**存储结构（③）最该学、且成本最低**；**编辑区（②）学的是"怎么改"而非"改不改"**（性能优化方向明确）；**导出（①）竞品的最优解反而和本项目路线冲突，只学一个"同源"思想、暂缓落地**。

| 块 | 竞品最佳实践 | 本项现状 | 借鉴价值 | 建议 |
|---|---|---|---|---|
| ③ 存储结构 | parent_id 版本树 + JD 独立持久化 | meta 仅 tags，无 parentId，JD 不落库 | **高（低成本高价值）** | **P1 立即做** |
| ② 编辑区 | iframe 沙箱 + 缩放；特征评分解析 | 直写 innerHTML，每键全量重渲染 | 中（方向对，工作量可控） | **P1 做性能收敛** |
| ① 导出 | 客户端 PDF（react-pdf），预览=导出同源 | 静默 PDF 依赖本地 Chrome；图片版不可选文字 | 低（依赖重，与护城河冲突） | **P2 暂缓，只记思想** |

## 一、③ 多简历托管与存储结构（最值得借鉴）

### 1.1 竞品做了什么

**Resume Matcher** 是这一块最清晰的参照系，它把"一份母简历 → 多份岗位定制版"做成了**数据库里的显式血缘关系**：

```
Master Resume（is_master = True）
        │  parent_id 指向
        ├── Tailored Resume A（投后端岗）
        ├── Tailored Resume B（投算法岗）
        └── Tailored Resume C（投管理岗）

Improvement Record（关联表）
   = master_resume + tailored_resume + job_description
```

三个关键设计点：

1. **`parent_id` 建血缘**：派生版不是"另一份孤立简历"，而是"挂在母简历下的子节点"。这带来三个能力：版本血缘追溯（这份定制版是从哪份母简历来的）、批量操作（对同一族简历统一改名/导出）、版本对比（子 vs 母 diff 出改了什么）。
2. **JD 单独持久化**（`job_id`）：职位描述不是一次性粘贴就丢的，而是作为独立实体存下来，**同一份 JD 可以反复对多份母简历定制**。
3. **Improvement Record 三方关联**：把「母简历 + 定制版 + JD」三者串成一条记录，这正是"哪种写法拿到了面试"反馈回路的数据底座。

**Reactive Resume** 补充了 schema 层的两个字段：`isPublic`（分享开关）、`isLocked`（锁定防误改），以及 schema 里的 `version` 字段做迁移。

### 1.2 本项目现状（已核对代码）

`js/store/resume-library.js` 的元数据结构：

```js
// create() 里新简历的 meta（:235）
var meta = { id, title, source: 'local', docId: null, updatedAt: Date.now(), tags: [] };
```

**问题**：
- **没有 `parentId`** —— 上一轮 A4 做的"JD 派生版本"（`resumeDeriveFromJd`）确实是"复制一份 + 插待补分组"，但复制出来的副本**和母简历之间没有任何血缘记录**。用户投了 5 个岗位生成 5 份定制版后，完全不知道哪份是从哪份来的、各自对应哪个 JD。
- **没有 `isMaster` / `source` 语义区分** —— `source: 'local'` 只是个占位，不能区分"这是母简历还是派生版"。
- **JD 不持久化** —— `js/jd-match.js` 的分析结果是内存态的，关掉 JD 面板或刷新就没了，无法"同一份 JD 反复用、投递后回溯"。
- **没有 `isPublic`/`isLocked`** —— A6 做的分享页是"导出一个静态 HTML"，但"哪份简历允许分享"没有在数据层标记。

### 1.3 结论与落地建议

**这是三块里性价比最高的一项**，因为：
1. 改动只在 `meta` 对象上加几个可选字段，**纯增量、向后兼容**（老数据没这些字段照样读）；
2. 直接服务于产品主线（JD 驱动一岗一简历），不是锦上添花；
3. 为将来 AI 阶段的"母简历 → 定制版"血缘打底（Resume Matcher 已经验证这是正确模型）。

**落地清单（建议下一步就做）**：

| # | 改动 | 说明 |
|---|---|---|
| S1 | `meta` 增加 `parentId`、`kind`（`master`/`tailored`）、`jobId`、`isPublic`、`isLocked` 可选字段 | `create`/`save` 透传，不写死 |
| S2 | A4 的 `resumeDeriveFromJd` 生成派生版时写入 `parentId=母id` + `kind='tailored'` + `jobId` | 补上血缘，改动约 10 行 |
| S3 | JD 文本独立持久化（复用 store 的一个分区，或 `data/jobs/<id>.json`） | 让"一份 JD 反复用"成立 |
| S4 | 简历库 UI 里对派生版加"母简历 / 对应 JD"的轻量标注 | 一眼看出血缘 |

> ⚠️ 提醒：`meta` 加字段会牵动 `save()` 里的元数据透传（`resume-library.js:262-278` 目前是白名单式赋值，每个新字段都要显式加一行）。这是本项目"新增字段必同步多处的"老规矩，做的时候一并补测试。

## 二、② 简历编辑区（方向对，学"怎么改"）

### 2.1 竞品做了什么

**OpenResume** 的预览系统（本次调研到组件级）：

- 预览放在 **iframe 沙箱**里（`ResumeIframeCSR`），A4 = 595×841pt，缩放用 `transform: scale`。iframe 的价值是**样式隔离**——预览区的 CSS 不会和编辑器 UI 的 CSS 互相污染。
- **PDF 组件化**：`ResumePDFProfile` / `ResumePDFEducation` / `ResumePDFWorkExperience` / `ResumePDFSkills`，样式集中在一个 `styles.ts`，保证"预览和导出长得一模一样"。
- **特征评分解析器**（`feature-scoring-system.ts`）：解析已有 PDF 时不是硬编码正则，而是对候选字段打特征分取最高分——这是它"结构化解析"准的原因（本项目 A3 已经借鉴了这个思想，落成了"低置信度标注 + 不臆造"）。

**Reactive Resume** 的编辑区关键洞察（v5.1.0 changelog）：

> "预览用 pdfjs 渲染**同一棵文档树**，消除了'预览看着对、导出就崩'这类 bug。"

这句话点破了编辑区设计的核心原则：**预览和导出必须是同一份渲染逻辑的两个视图，而不是两套代码**。

### 2.2 本项目现状（已核对评估文档 §4.4）

```
input 事件 → renderPreview() → preview.innerHTML = 全量 HTML
     └→ RB.saveState() → contentHash → stableHash = O(整份简历)/键
     └→ drawPageGuides() → computePageBreaks() 逐个读 offsetTop → 强制 reflow
     └→ MutationObserver + ResizeObserver → applyPreviewScale() → 又一次 reflow
```

**问题（评估文档已诊断，未修）**：
1. 每敲一个键 = 全量 innerHTML + 全量哈希 + 2~3 次强制 reflow，**长简历卡顿主因**；
2. 只有写盘有 800ms debounce，渲染和分页线没有；
3. 预览直接写 `preview.innerHTML`，没有 iframe 沙箱隔离（不过本项目的 CSS 命名是 `.resume` 前缀，隔离问题目前不严重，不是首要矛盾）。

### 2.3 结论与落地建议

**iframe 沙箱和 react-pdf 组件化不用照搬**——那是 React 技术栈的解法，本项目"原生 JS + file:// 直开"的护城河决定了不能引 react-pdf。但有两个**思想**值得落地：

1. **「预览 = 导出同源」的思想**：本项目的 PDF/长图导出已经走"克隆 .resume 再截图"（`makeCaptureClone`），本质上接近同源；真正要补的是**图片版 PDF 的文字不可选**问题（见 §三）。
2. **性能收敛（这是真正该做的）**：把"每键全量重渲染 + 全量哈希 + 多次 reflow"收敛掉。这是评估文档 P1 #9 已列、尚未落地的一项。

**落地清单**：

| # | 改动 | 说明 |
|---|---|---|
| E1 | `saveState` 的 `contentHash` 从"每键全量"改为**防抖 + 增量**（内容指纹可延迟算） | 消除 O(整份简历)/键 |
| E2 | `drawPageGuides` / `computePageBreaks` 移出每键路径，进 `requestAnimationFrame` 空闲回调 | 消除强制 reflow |
| E3 | 分页线只在**内容变化后**重算，不在每次 input 时算 | 同上 |

> 这一项和竞品无关、纯属本项目自己的技术债，但评估文档把它列在 P1 且长期没动，趁这次一起定位。

## 三、① 简历导出（PDF / 图片）

### 3.1 竞品做了什么

**Reactive Resume v5.1.0 是这条线的标杆**：

- **PDF 生成完全客户端化**（`@react-pdf/renderer`），**彻底去掉了 headless Chrome / Browserless / Puppeteer 依赖**；
- 预览用 pdfjs 渲染**同一份文档树**，所以"预览看到的 = 下载到的"；
- 代价是：**放弃了自定义 CSS**（因为不再走浏览器打印，raw CSS 不生效），只能靠模板的「结构化定制」来改样式。

**OpenResume** 同样是 react-pdf 纯前端出 PDF（真矢量、文字可选中），并把"ATS 可读性"当卖点。

### 3.2 本项目现状（已核对）

本项目导出分两类：

| 方式 | 实现 | 特点 |
|---|---|---|
| 静默 PDF | `tools/serve.js` `/api/pdf` 调本机 Chrome headless 打印 | 文字可选中、矢量，**但依赖本地 Chrome + npm start**，无 Chrome 就报 501 |
| 图片版 PDF / 长图 | html2canvas 截图拼合 | 版式 100% 一致，**但文字不可选、体积大** |
| 单文件 HTML | 克隆 .resume + 内联 CSS | 文字可选中，但不是 PDF |

**这正好踩中了竞品已经解决的两个痛点**：
1. **静默 PDF 依赖 headless Chrome**——这正是 Reactive Resume v5.1.0 之前的老架构，人家已经证明这条路又重又脆（本项目 `printToPdf` 里还专门写了"Chrome 打印完不退出、轮询等待产物"的 workaround）。
2. **图片版 PDF 文字不可选**——OpenResume 用 react-pdf 解决的就是这个。

### 3.3 结论与落地建议

**这一块要克制，不能照搬**，原因：

1. **react-pdf 是 React 生态**，引入它 = 打破本项目"原生 JS + 零依赖 + file:// 直开"的护城河（这是方案文档里明确写死"不引框架"的决策）。
2. **本项目的自定义 CSS 是核心竞争力**（用户就是想要"颠覆传统布局"的自由排版），而 Reactive Resume 走客户端 PDF 的代价恰恰是"放弃自定义 CSS"。**两者本质冲突**——你要自由排版，就得走浏览器打印；要走纯前端矢量 PDF，就得放弃自由 CSS。
3. 纯前端出**矢量 PDF** 在零依赖下没有好方案（PDF 文字排布、中文字体嵌入都是重活，等于自己写半个浏览器排版引擎）。

**所以正确的策略是"保留现状 + 补一个小的"**：

| 优先级 | 动作 | 说明 |
|---|---|---|
| 保持 | 静默 PDF（Chrome headless）继续用 | 它是"文字可选中 + 矢量 + 自由 CSS"三者的唯一交集，竞品用客户端 PDF 换不来自由 CSS |
| P2（可选） | 给"图片版 PDF"补一个**文字可选中**的替代路径 | 即"单文件 HTML → 用户手动 Ctrl+P 另存为 PDF"，这个已经存在（单文件 HTML + 打印样式），只需在导出弹窗里**引导**一下，而不是新造引擎 |
| 明确不做 | 引入 react-pdf / 客户端 PDF 引擎 | 与护城河冲突，且放弃自由 CSS 得不偿失 |

> 一句话：竞品在"导出"上的最优解，是建立在"放弃自由 CSS、拥抱模板化"之上的；而你的核心诉求恰恰是"自由 CSS、颠覆布局"。所以这一块**别人做得再好，也不该照抄**——守住静默 PDF + 自由 CSS 的组合，才是你的差异化。

## 四、综合建议（按落地优先级）

| 优先级 | 落地项 | 借鉴来源 | 预估成本 | 价值 |
|---|---|---|---|---|
| **P1（立即）** | 存储血缘：`parentId`/`kind`/`jobId` + JD 持久化 + 派生版回溯 | Resume Matcher | 0.5~1 天 | 高，服务产品主线 |
| **P1** | 编辑区性能：`saveState` 防抖 + 分页线 rAF + 增量哈希 | Reactive Resume（同源思想引申） | 1~2 天 | 中，真实卡顿 |
| **P2（暂缓）** | 导出引导：图片版 PDF 旁提示"文字可选中请用打印" | 无（纯 UX） | 0.5 天 | 低 |
| **不做** | react-pdf 客户端 PDF、iframe 预览、服务端账号 | 三家共性 | — | 与护城河冲突 |

## 五、给用户的一句话总结

三个高星项目在**存储结构**上给了我一个明确该抄的东西——**用 `parent_id` 把"母简历 → 岗位定制版"的血缘建起来，并让 JD 单独持久化**（Resume Matcher 已经证明这是"一岗一简历"的正确数据模型，而你上一轮 A4 做的派生版恰好缺了这一层血缘）。**编辑区**该做的是性能收敛（每键全量重渲染是老技术债）。**导出**别人走得最远（纯客户端 PDF），但它建立在"放弃自由 CSS"之上，和你要的"颠覆布局"正好冲突——所以这一块**该守、不该抄**。
